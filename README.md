# Агент образовательных программ АЦР

Методист пишет «программа повышения квалификации на 72 часа по анализу данных
для сотрудников банков» — агент возвращает готовый комплект: программу в .docx
по шаблону Академии, учебный план с часами, карту компетенций, тесты с ключами,
задания семинаров, планы лекций и слайды.

Задача хакатона — [docs/case-task.md](docs/case-task.md).

## Главное решение

Модель пишет тексты. Числа считает код.

Часы распределяет солвер, а не модель: суммы по темам, модулям и видам работы
сходятся с заказанным объёмом конструктивно, а не по удаче. Нормативные акты и
коды профстандартов берутся из реестра — чего там нет, в документ не попадает,
неподтверждённое помечается «требует проверки методистом».

Модели отдают строку вместо объекта, забывают форму обучения, недодают
вопросов, требуют практику там, где аудиторных занятий нет. Каждый такой
случай закрыт кодом и тестом: `tests/test_model_discipline.py`,
`tests/test_intake_without_model.py`.

## Запуск

На площадке хакатона (docker без compose, порт 8000):

```bash
make deploy          # сохраняет готовый .env; при отсутствии создаёт из ai.env
make logs            # журнал бэкенда
make stop
```

Через docker compose — `.env` рядом с `docker-compose.yml`, образец в
`backend/.env.example`:

```bash
docker compose up -d --build       # http://localhost:3100
```

Без ключа модели сервис поднимается на офлайн-заглушке — это видно в
`/api/health`, плашкой в интерфейсе и пометкой «черновик» в выгрузках.

Для разработки:

```bash
cd backend && LLM_PROVIDER=mock uvicorn app.main:app --reload --port 8000
cd frontend && npm install && npm run dev
```

## Безопасный запуск в целевой среде

**Обязательно:**

```
OPENAI_BASE_URL     адрес шлюза Cloud.ru или площадки
OPENAI_API_KEY      ключ
OPENAI_MODEL        модель из каталога, например GigaChat/GigaChat-3-Pro
METRICS_TOKEN       иначе раздел статистики закрыт
```

**Что проверяется при старте.** Неверная конфигурация останавливает запуск
с объяснением, а не уводит сервис в неожиданный режим:

- адрес модели вне Cloud.ru и шлюза площадки — отказ. Выключателя этой
  проверки нет. Тестовый профиль `yandex_dev` разрешает только API Yandex.
  `LLM_EXTRA_HOSTS` не расширяет адреса профиля. Журнал запуска пишет строку «проверка хоста:
  <хост> — разрешён: <правило>», `/api/health` отдаёт `llm_host` и
  `llm_host_rule`;
- логин или пароль в адресе модели, схема не http(s) — отказ; `http://`
  не на localhost — предупреждение;
- провайдер сверяет хост ещё раз сам, а перенаправления шлюза (3xx) не
  выполняет: ключ не уходит на адрес, который проверку не проходил;
- ключ без адреса или модели — отказ, а не тихий переход на заглушку;
- `LLM_PROVIDER=mock` при заданном ключе — отказ;
- числа вне допустимого диапазона или не числа — отказ с указанием
  переменной и диапазона;
- устаревшие переменные (`LLM_ALLOW_ANY_HOST`) — отказ с подсказкой замены.

**Для сдачи в `.env` не должно быть:**

```
LLM_PROFILE=yandex_dev   тестовый VPS, не профиль сдачи
LLM_CACHE=1         повторные запросы берутся с диска, генерация не настоящая
LLM_PROVIDER=mock   офлайн-заглушка
```

Если что-то из этого задано, сервис предупреждает при старте.

**Как убедиться, что запуск правильный:**

```bash
docker logs backend 2>&1 | head -12
```

В сводке — адрес шлюза, модель, обрезанный ключ и ни одной строки с `!`.
Затем:

```bash
curl -s localhost:8000/api/health
```

Ожидается `"llm_provider": "openai_compat"` и `"offline_stub": false`.

**Ключи и данные:**

- `.env` в `.gitignore`; в репозиторий попадает только `backend/.env.example`
  без значений;
- ключ печатается в журнале обрезанным и вычищается из любых текстов
  ошибок — в интерфейс, сессию и телеметрию он не попадает;
- кэш ответов выключен по умолчанию; включённый — хранит записи 24 часа,
  не больше 2000 файлов, с правами только для владельца;
- сессии пишутся атомарно, идентификатор сессии проверяется по форме —
  выйти за пределы каталога данных через URL нельзя;
- статистика закрыта токеном: в ней тексты запросов методистов и стоимость.

## Переменные

Полный список с допустимыми диапазонами — `backend/app/config.py`;
все переменные передаются в контейнер через `docker-compose.yml`.

| Переменная | По умолчанию | Зачем |
| --- | --- | --- |
| `OPENAI_BASE_URL`, `OPENAI_API_KEY`, `OPENAI_MODEL` | — | доступ к модели; `LLM_*` тоже принимаются |
| `METRICS_TOKEN` | — | доступ к статистике |

| `SLIDE_TOPICS` | 2 | первых тем со слайдами |
| `MAX_CLARIFYING_QUESTIONS` | 5 | уточняющих вопросов за раз, чек-лист кейса — не больше 5 |

а не правка кода.

## Выбор модели

В профиле `hackathon` в поле ввода рядом с кнопкой отправки можно выбрать **GigaChat 3 Pro** или
**GigaChat 3.5 Reasoning**. Выбор сохраняется у программы и применяется к
следующим действиям агента: уточнениям, каркасу, материалам, правкам и
экспертной проверке. Готовые материалы автоматически не пересоздаются.
Адаптированная программа наследует модель исходной. Во время операции
переключение заблокировано. Последний выбор браузера используется для новых программ.

Обе модели используют существующие `OPENAI_BASE_URL` и `OPENAI_API_KEY`;
ключ должен иметь доступ к обеим моделям на этом шлюзе. `OPENAI_MODEL`
задаёт выбор по умолчанию строго из этих двух моделей. Любая другая модель,
включая Yandex и embeddings, отклоняется API и настройками запуска сервера
в профиле `hackathon`. В `yandex_dev` доступна только одна серверная модель
`gpt://<folder-id>/yandexgpt/latest`; в поле ввода отображается «YandexGPT»
без переключателя. Добавления моделей через интерфейс или API нет.
Разрешение дополнительного домена шлюза не расширяет каталог моделей.
В офлайн-режиме выбор сохраняется, но обе позиции работают на заглушке.

API: `GET /api/models` — каталог; `POST /api/sessions/{id}/model` с
`{"model_id":"ai-sage/GigaChat3.5-432B-A28B-Reasoning"}` — смена модели.
`POST /api/sessions` и `POST /api/generate` также принимают `model_id`.
Произвольные идентификаторы вне каталога отклоняются. Выбор изолирован
контекстом операции; лимит параллельных запросов общий, кэш разделён по моделям.

Reasoning получает дополнительно 8192 токена к бюджету ответа и таймаут
чтения не меньше 300 секунд. Используется только итоговый `message.content`;
поля рассуждений не подставляются в документы. Формат сверялся с
[официальной карточкой модели](https://huggingface.co/ai-sage/GigaChat3.5-432B-A28B-Reasoning).
Доступность и особенности конкретного шлюза требуют живой проверки.

Расчёт стоимости сохраняется для каждого вызова, поэтому смена модели не
пересчитывает прошлые расходы. Тарифы в `backend/app/llm/catalog.py` взяты из
предоставленного каталога на 28.10.2026: Pro — 73,03 / 176,39 ₽,
Reasoning — 96,22 / 288,60 ₽ за миллион входных / выходных токенов.
Это оценка по токенам, которые сообщил шлюз, а не баланс счёта; тарифы
не обновляются автоматически. Для старых записей сохраняется расчёт
по резервным переменным цены. Стоимость офлайн-заглушки — ноль.

## Два окружения: VPS и ВМ хакатона

Сначала обновите исходники на сервере. Настройки относятся к корневому `.env`
рядом с `docker-compose.yml`, а не к `backend/.env.example`.

На тестовом VPS в `/opt/gigaschool/.env` добавьте `LLM_PROFILE=yandex_dev`.
Сохраните текущие `LLM_BASE_URL=https://llm.api.cloud.yandex.net/v1`,
`LLM_MODEL=gpt://<ваш-folder-id>/yandexgpt/latest`, `LLM_AUTH_SCHEME=Api-Key`,
ключ и токен статистики. Для Compose задайте `WEB_PORT=3100`.
Полный образец без секретов — `backend/.env.yandex.example`.

На ВМ в `~/project/.env` задайте `LLM_PROFILE=hackathon`,
`OPENAI_MODEL=GigaChat/GigaChat-3-Pro`, `LLM_AUTH_SCHEME=Bearer` и
`WEB_PORT=8000` (последнее — для Compose). Адрес и ключ площадки остаются
прежними: `/opt/hackathon/ai.env`. Параллельные `LLM_MODEL`, `LLM_BASE_URL`,
`LLM_API_KEY` имеют приоритет над `OPENAI_*`; не оставляйте в них значения VPS.
Без `LLM_PROFILE` действует строгий профиль хакатона. Неизвестный профиль
останавливает запуск; автоматического перехода к другому провайдеру нет.

Пересоберите **тем же способом, которым запускали**:

- Compose: `docker compose up -d --build backend frontend`.
- Makefile: `make deploy PORT=8000` на ВМ или `make deploy PORT=3100` на VPS.

`make deploy` теперь сохраняет существующий `.env` целиком, включая профиль,
ключи и токен статистики. При первом запуске на ВМ он создаёт файл из
`/opt/hackathon/ai.env`. Перезапуск без пересоздания контейнера не обновляет его
окружение. Проверка: `/api/health` отдаёт `llm_profile`, `/api/models` —
две модели хакатона или одну YandexGPT. Это проверка конфигурации, а не доступа
ключа к живой модели. Ключи через эти ответы не раскрываются.

## Как устроен путь

Каждый шаг — отдельный навык со своей инструкцией в `app/skills/*.yaml`.

```
запрос методиста
  intake      разбор параметров, не больше 5 уточняющих вопросов
  skeleton    цель, результаты обучения, компетенции, модули и темы
  солвер      часы по модулям, темам и видам работы + автопроверка
  ────────── методист утверждает каркас ──────────
  content     содержание тем, тесты, семинары, планы лекций, слайды
  автопроверка полного комплекта
  выгрузки    .docx · .pptx · GIFT · CSV · JSON
```

Пересборка одной темы, без остального комплекта:
`POST /api/sessions/{id}/topics/{topic_id}/regenerate`.

## Автопроверка

`app/core/validate.py`, 33 кода:

- суммы часов на всех уровнях, включая итоговую строку с аттестацией; сверка
  встроена и в саму структуру — `program.hours_check` едет в каждой выгрузке JSON;
- каждый результат обучения раскрыт темой и проверяется двумя оценочными средствами;
- сквозная трассировка компетенция → РО → оценочное средство: ссылки в никуда,
  расхождение сторон связи, компетенция, которую проверяет только итоговая аттестация;
- источники и профстандарты существуют;
- разделы шаблона заполнены (свои наборы для ДПП ПК и общеразвивающей);
- реквизиты приказа, ФИО и подписи остаются незаполненными;
- календарный график не противоречит объёму.

Ошибка блокирует переход к содержанию, предупреждение уходит в отчёт методисту.

## API

Интерфейс ходит по шагам (`/api/sessions/...`), для машинной проверки есть один
вход:

```bash
curl -X POST localhost:8000/api/generate -H 'Content-Type: application/json' \
  -d '{"text": "программа повышения квалификации на 72 часа по анализу данных на Python для сотрудников банков, очно-заочно, защита проекта"}'
```

Данных хватает — придёт `status: "ready"` с программой, отчётом и ссылками на
выгрузки. Не хватает — `status: "need_answers"` с вопросами; ответы досылаются
вторым вызовом на тот же адрес с `session_id`.

Работа с готовой программой:

```
POST /api/sessions/{id}/topics/{topic_id}/regenerate   переделать тему по пожеланию
POST /api/sessions/{id}/adapt                          под другую аудиторию или объём
POST /api/sessions/{id}/refresh                        найти устаревшее
POST /api/refresh/upload                               то же для старой программы файлом
GET  /api/sessions/{id}/sources/pending                что методисту сверить и где
POST /api/sessions/{id}/sources/review                 подтвердить источник или убрать
```

Адаптация создаёт новую сессию, исходная программа не меняется. Актуальность
определяется по знаниям модели и помечается как требующая проверки методистом.

## Проверки

```bash
cd backend
python -m pytest tests -q                   # 370 тестов, заглушки, без сети
python scripts/run_open_requests.py         # 5 запросов кейса, 92 проверки по чек-листам
```

Тесты изолированы от окружения: ключ в терминале не уведёт их в живую модель.

Отладка без обращений к модели:

```bash
python scripts/replay_model_answer.py --case 2 --drop study_form --skeleton
python scripts/probe_parallel.py --levels 1 2 4
```

Первый прогоняет запрос на заранее заданном ответе модели, второй измеряет,
сколько одновременных запросов пускает шлюз.

Собрать комплект файлами, без браузера:

```bash
python scripts/generate.py --type pk --hours 72 --title "Анализ данных" --out ../out
```

## Совместная работа и экспертная проверка

Методист по-прежнему самостоятельно собирает и выгружает программу на подпись.
Экспертиза и согласование внутри сайта — дополнительные сценарии, они не
добавляют обязательных этапов к генерации или экспорту.

После сборки программы в боковой панели доступны:

- **Экспертиза** — маршрут по темам, материалам, тестам с ключами, практическим
  заданиям, слайдам и итоговой аттестации. Агент анализирует тему вместе со
  связанными заданиями. Замечания с дословными цитатами — гипотезы для эксперта,
  просмотр и отсутствие замечаний не означают «проверено». По умолчанию темы
  свёрнуты; можно согласовать весь комплект, тему или выбранные галочками
  материалы. При чтении закреплена панель «Согласовать и дальше / Пропустить».
  Пакетное решение сохраняется отдельно от факта индивидуальной проверки;
  предыдущие комментарии остаются в истории. Кнопка «Спросить агента» даёт
  объяснение без изменения материала.
- **Правки эксперта** — предложения с редакциями «было / предлагается».
  Только принятие методистом меняет общую программу и последующие выгрузки.
  Ручное редактирование доступно без модели; у тестов отдельно редактируются
  варианты, ключи и объяснение.
- **Согласование** — сводка программы, результаты проверки, история решений,
  возврат с замечанием и согласование текущей версии. Это запись решения,
  а не электронная подпись; подпись руководителя оформляется в документе.
  После решения доступен лист согласования DOCX с названием, именем участника,
  датой, версией и сводкой экспертизы на момент решения. При последующем
  изменении программы лист указывает, что согласование относится к прошлой версии.

Кнопка «Ссылка эксперту» формирует адрес `#/expert?session=…`, для руководителя
есть `#/approval?session=…`. Открытие ссылки и перезагрузка восстанавливают
серверную сессию. Для получения последних изменений другого участника есть
кнопка «Обновить»; отправка решения всегда проверяет версию на сервере.

Результаты, предложения и история согласований сохраняются вместе с сессией.
Изменение материала делает его проверку неактуальной; изменение текста темы
также требует пересмотра связанных заданий. Старую правку нельзя принять
поверх новой версии. Согласование руководителя привязано ко всей программе.

**Граница этой версии:** рабочие экраны доступны по ссылке на сессию. Имя
участника вводится самостоятельно, аккаунтов и разграничения прав по ролям
пока нет. Переключение экранов удобно для демонстрации и не является проверкой
