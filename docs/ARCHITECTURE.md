# Архитектура

## Решения и их обоснование

### 1. ProgramIR как единый источник правды
Все выгрузки (.docx, .pptx, GIFT, CSV, JSON) читают одну структуру —
`app/schemas/ir.py`. В кейсе отдельная проблема в том, что комплект готовят
разные люди в разных файлах, отсюда повторы и рассогласование. Один объект
убирает эту возможность: материалы не могут разойтись, потому что они
производные одного состояния.

### 2. Часы считает код, а не модель
`app/core/hours.py` раскладывает часы методом наибольших остатков в единицах
0.5 или 1 ак. ч, поэтому сумма частей **конструктивно** равна целому.
Модель даёт только относительные веса модулей и тем и пропорцию видов работы.

Почему так: в действующей программе АЦР (образец стажировки) итоговая строка
учебного плана не сходится со строками модулей. Это типовая ошибка ручной
сборки, и в чек-листах кейса арифметика стоит первым пунктом. LLM не даёт
гарантий на арифметику ни при какой температуре, детерминированный солвер даёт.

Остаток от деления уходит в итоговую аттестацию, часы выравниваются по зерну —
иначе «потерянные» 0.5 ч всплывают в итоговой строке.

### 3. Жёсткие ограничения важнее мнения модели
Если в запросе сказано «16 часов, занятия по 2 часа два раза в неделю», то
8 × 2 = 16 — самостоятельной работы в программе быть не может. Такие выводы
делает код (`contact_only`, `_mix_weights`), а не промпт. То же с требованием
«практики не меньше половины» и со стажировкой без аудиторных часов.

### 4. Реестр вместо памяти модели
`app/registry/legal.py` хранит проверенные реквизиты нормативных актов и
профстандартов. Модели запрещено называть номера приказов. Статусы:

- `verified` — реквизиты подтверждены (образцом АЦР, ТЗ кейса);
- `unverified` — запись есть, реквизиты требуют сверки → печатается с пометкой
  «требует проверки методистом»;
- `rejected` — кода нет в реестре → в документ не попадает.

Так выполняется запрет кейса на выдуманные источники без риска «честно
придумать» номер приказа.

### 5. Человек в контуре как состояние, а не как просьба
У сессии есть стадии (`app/store.py`): `clarifying → skeleton → approved →
content → ready`. Переход к содержанию закрыт, пока методист не утвердил
каркас, а `approve` отклоняется, если автопроверка нашла ошибку. Это не
рекомендация в промпте, а инвариант API.

### 6. Навыки как единицы конфигурации
Каждый шаг — YAML-файл с инструкцией и шаблоном входа (`app/skills/`).
Причины: логика переносится в GigaCowork, где навык — единица настройки;
инструкцию можно править, не трогая код; шаги независимы, поэтому одну тему
можно пересобрать отдельно.

### 7. Адресуемость и точечная доработка
Каждый узел IR имеет идентификатор (`M-1`, `T-1.2`, `RO-3`, `Q-7`).
Пересборка темы удаляет только её производные (вопросы, задания, слайды с
этим `topic_id`) и генерирует заново. Остальной комплект не затрагивается,
после чего автопроверка прогоняется целиком.

### 8. Параллелизм под тайминг кейса
Каркас — один вызов модели (укладывается в 3 минуты). Содержание —
fan-out по темам с семафором на 4 одновременных вызова, поэтому время растёт
не линейно по объёму программы.

### 9. Провайдер LLM за интерфейсом
Запрет на зарубежные API — архитектурное требование, а не деталь настройки.
`app/llm/base.py` задаёт контракт, `openai_compat.py` работает с любым
OpenAI-совместимым эндпоинтом (Yandex для разработки, Cloud.ru для сдачи),
`mock.py` даёт офлайн-демо и детерминированные тесты.

## Потоки данных

```
POST /api/sessions                 → intake → параметры + вопросы
POST /api/sessions/{id}/answers    → применение ответов методиста
POST /api/sessions/{id}/skeleton   → skeleton + солвер + автопроверка
POST /api/sessions/{id}/approve    → гейт (блокируется при ошибках)
POST /api/sessions/{id}/content    → фоновая генерация комплекта
GET  /api/sessions/{id}/events     → SSE-прогресс по шагам
GET  /api/sessions/{id}/export/*   → docx | pptx | gift | csv | json
POST /api/sessions/{id}/topics/{topic_id}/regenerate → точечная доработка
```

## Что осознанно не сделано

- **Хранилище** — файловое. Для демо и прогона тестовых запросов достаточно;
  интерфейс `SessionStore` меняется на Postgres без правок вызывающего кода.
- **RAG по референсам** — пока разбор структуры (`pipeline/references.py`),
  без эмбеддингов. Эмбеддинги нужны для сравнения с чужими курсами
  (проверка на дословное копирование) — это следующий шаг.
- **Проверка существования источников онлайн** — реестр локальный; в проверочной
  среде доступ в интернет не гарантирован, поэтому неподтверждённое помечается,
  а не выдумывается.
